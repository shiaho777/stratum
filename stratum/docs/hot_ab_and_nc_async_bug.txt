Hot-regime 27B A/B + the NC_ASYNC stale-y corruption bug
==========================================================
Date: 2026-09-08 (config recorded per AGENTS.md "Recording experiment
configuration")

Part 1 — The hot-regime measurement finally ran (and what it showed)
---------------------------------------------------------------------
Machine state at measurement: swap 94% (15.4/16.4GB), but free+inactive
reached 12.65GB — the best window of the session, enough for the 11.2GB
model to approach full residency. Three warm-up runs pushed weight-cache
residency 69% -> 78% -> 99%; hot_fast engaged at 99%.

Config (all runs): qwen3.6-27b-mixed.gguf, prompt "1 2 3 4 5 6 7 8",
STRATUM_NOSPEC=1, greedy; NC runs add STRATUM_GPU_NC=1 + Q2K/Q4K/Q6K
COAL=1 (+ V57 batching, merged in PR #58). External wall timing.

  run                          | wall (8 tok) | sequence
  -----------------------------+--------------+---------------------------
  NC+COAL+V57 (resident 99%)   |    38.6s     | 10 4838 1665 25 33898 ...
  CPU       (resident 99%)     |    20.7s     | identical
  NC+COAL+V57+NC_ASYNC (pre-fix)|   25.9s     | CORRUPT (69582 32969 ...)

Findings:
  1. CPU beats NC by 1.86x even "hot" — but the hot label is misleading:
     20.7s/8tok ~= 2.1s/token marginal = ~5.3 GB/s effective = SSD speed,
     NOT the ~200 GB/s page-cache speed. On a swap-saturated machine the
     model does not STAY resident: other processes' paging continuously
     evicts it mid-run. Both arms were streaming; NC's GPU page-in path
     thrashes worse than CPU faults.
  2. Run-to-run variance is extreme (a later CPU n=8 run took 7.9s vs
     n=4's 19.1s — cache state swings between runs). Precise hot A/B is
     not measurable while the machine swaps.
  3. Conclusion: on THIS machine state, CPU is the correct default (the
     engine's shipped default is right). The NC+COAL kernel-bandwidth
     advantage (170-245 GB/s, probe-measured) can only materialize on a
     machine where the model actually stays resident. That measurement
     remains open; nothing in the engine blocks it.

Part 2 — NC_ASYNC silently corrupted output (found + fixed)
------------------------------------------------------------
The NC_ASYNC run above produced a completely wrong sequence (69582
32969 56194 ... instead of 10 4838 1665 25) while running FASTER
(25.9s) — the classic signature of skipped waits.

Root cause: STRATUM_NC_ASYNC=1 makes stratum_metal_nc_batch_flush()
commit-only (wait + y copy-back deferred to the next begin). Every
qwen35 batch window consumes its y results IMMEDIATELY after flush
(q-split memcpy, swiglu, residual add) — so consumers read stale y.
Pre-V57 this was latent: B=1 never opened batch windows (hot_fast
short-circuit), and NC_ASYNC had only ever been exercised by the H3
spikes (separate binaries whose consumers sit after the next-begin
drain). V57's B=1 windows made the hazard reachable in the main engine.

Fix (V57.1): call stratum_metal_nc_batch_consume() — the engine's
existing purpose-built fence ("same wait + copy-back as drain, safe
between a flush and its immediate CPU consumer, no-op in sync mode") —
after every qwen35 window flush: q35_nc_flush() and the two group
functions (q35_gpu2_group_multix_nc, q35_gpu_nc_group_b1).

Validation:
  - tiny qwen35 Q4_K: NC_ASYNC on/off greedy sequences identical
    (287 345 335 780 554 915)
  - 27B 4-token: NC+COALs+NC_ASYNC sequence restored to the baseline
    (10 4838 1665 25), wall 20.2s
  - make tests 4/4 PASS

Lesson recorded: any new batch window in this engine MUST pair its
flush with consume() unless the consumer provably runs after the next
begin()'s drain. Async submission is an overlap optimization, not a
license to skip the copy-back fence.


Part 3 — The NC in-engine pathology: measured decomposition (V58 work)
-----------------------------------------------------------------------
With the model at 100% residency (first clean window of the session),
NC + all three COAL kernels measured 3.2s/token marginal vs CPU 0.465s
— NC is ~7x SLOWER in-engine despite its kernels probing at 170-245
GB/s. STRATUM_TIMING + the (previously never-called) nc_time_report
decompose it:

  [nc-time] NoCopy reg: 632 x 11.0us = 0.007s   <- cheap, NOT the problem
            commit+wait: 320 x 6.0ms = 1.92s    <- 15x the probe's 0.4ms
  [fwd B=1] wall=2.5-3.0s  gpu=0.22  cpumm=0.20  iostall=0.11-0.19
            (all tracked buckets sum ~0.75s — ~1.8s/forward UNTRACKED)

V58 (STRATUM_NC_WCACHE=1): reuse one MTLBuffer per distinct aligned
window instead of creating a fresh NoCopy window per dispatch (hash on
aligned ptr; opt-in; bounded by tensor count):
  commit+wait 6.00 -> 5.25ms avg (-12%); NoCopy reg 11.0 -> 3.2us.
  Sequences identical. Helps, does NOT cure.

Remaining suspects for the 5.25ms commits + 1.8s untracked (ranked):
  1. Per-layer I/O scheduling calls (io_tpl_kick_layer, wt_next_start,
     layer_tail_hide, main_scan_warm, tensor_pages_hot/mincore) still
     run under hot_fast — it only short-circuits multix_pipe, not the
     layer-block calls. mincore over GPU-windowed pages may serialize
     against VM state.
  2. GPU page-in during kernels: at 81-100% residency the tail % of
     weight pages still fault via the GPU at SSD speed inside
     commit+wait (the wait absorbs it).
  3. Command-buffer lifecycle at ~29 commits/forward: each begin/flush
     allocates and tears down driver objects; probes reused patterns.
The CPU path's advantage in this regime is that its "overhead" (page
faults) IS its I/O, while NC pays fault-equivalent costs PLUS the GPU
submission stack. Until the untracked 1.8s is attributed, CPU remains
the correct default and NC stays opt-in.

Part 4 — zsh word-splitting trap (cost a full A/B session)
-----------------------------------------------------------
`env $VARS ./stratum ... $P` in zsh does NOT split unquoted parameters:
the whole env string became ONE assignment (only the first flag took
effect, value contaminated) and the prompt collapsed to its first
token. An entire manual hot A/B ran three "configs" that were actually
one. Fixed in benchmarks/hot_ab_27b.sh via ${=VAR}; recorded here
because every future shell-driven measurement on this repo must use
${=...} (or arrays) for env/prompt expansion under zsh.


Part 5 — The decisive hot A/B (clean same-cache-state) + V59 refuted
----------------------------------------------------------------------
Machine state: model warmed to 95-100% residency, hot_fast ENABLED,
all runs back-to-back in one cache window. 27B, prompt 1..8, NOSPEC,
greedy; NC runs add the three COAL flags. STRATUM_TIMING per-forward:

  config              | fwd wall | tracked buckets          | sequence
  --------------------+----------+--------------------------+-----------
  CPU hot             |  0.468s  | cpumm 0.366 (Q2 5.23G +  | 10 4838
                      |          | Q4 3.11G + Q6 1.96G all  | 1665 ...
                      |          | on CPU, 28 GB/s)         |
  NC hot (V56 behav.) |  2.024s  | gpu 0.355, commit+wait   | identical
                      |          | ~0.2-0.3, rest ~0        |
  NC hot (V59 ioskip) |  3.617s  | iostall 0.333 REAPPEARS, | identical
                      |          | CPU weights 7.4GB        |

Conclusions:
  1. CPU hot is 4.3x FASTER than NC hot on the 27B (0.468 vs 2.024
     s/forward), sequences identical. The engine's CPU default is right.
  2. The non-matmul compute (SSM scan + attention + elementwise) is only
     ~0.1s/forward (CPU fwd 0.468 - cpumm 0.366) — so the NC path's
     ~1.6s untracked is NOT model compute. It lives in the NC submission
     stack: ~130 begin/flush/consume window lifecycles + ~350 encoder
     cycles per forward, each pathologically slow on this machine
     (commit+wait 6.1ms avg vs 0.4ms in probes). Attributing the rest
     needs Metal-level profiling (Instruments/signposts) — beyond shell
     instrumentation.
  3. V59 (skip layer I/O scheduling under hot_fast) is REFUTED and ships
     default-OFF (opt-in STRATUM_HOT_FAST_IOSKIP=1): the scheduling is
     LOAD-BEARING for NC — wt_next_start's preads keep the next tensors
     resident, and newBufferWithBytesNoCopy FAILS on non-resident
     file-backed pages, so with ioskip ON ~300 dispatches fell back to
     CPU (NoCopy reg 632->334, CPU weight bytes 0->7.4GB, iostall
     reappears, wall 28.8->34.8s). The V56 author's "pure tax" note
     applies to the multix_pipe decision chain only — not to the pread
     residency maintenance the GPU path depends on.
  4. Net session verdict on single-stream: on this machine the honest
     hot number is CPU ~2.1 tok/s marginal (0.468s/fwd). NC's kernel-
     level wins (170-245 GB/s probes) are real but swamped by the
     in-engine submission-stack overhead; making NC win requires
     profiling that stack (next session's first move: Metal signposts
     around begin/encode/flush/consume).


Part 6 — V60 submission-stack decomposition (begin/encode/copy-back timers)
----------------------------------------------------------------------------
Added metal-side timers (printed by nc_time_report under STRATUM_TIMING):
begin (drain-check + command-buffer alloc), copy-back (flush/drain memcpy
loops); encode is already bounded by the engine's gpu= bucket (it wraps
add_streams end-to-end).

27B NC run (residency had decayed to 43% — a streaming-regime sample):
  NoCopy reg:    331 x 70.4us = 0.023s
  commit+wait:   320 x 5.77ms = 1.846s   <- the dominant metal-side cost
  begin:         320 x 8.1us  = 0.003s   <- REFUTES cmd-buffer-alloc theory
  copy-back:                  = 0.003s   <- negligible
  fwd wall 3.4-3.8s; tracked buckets ~1.0-1.1s + commit ~0.37s/fwd.

Conclusions:
  1. begin and copy-back are NOT the untracked time (ruled out, us-scale).
  2. commit+wait at 5.8-6.7ms avg (vs 0.4ms for identical kernels in
     probes) is the single largest metal-side anomaly. The wait absorbs
     GPU execution INCLUDING page-ins; at 43% residency the GPU faults
     weights from SSD inside the wait.
  3. NoCopy reg count is a residency canary: 632 regs at 99% residency
     vs 331 at 43% — failed NoCopy creations (non-resident pages) fall
     back to CPU (6GB CPU weights in this run). Reconfirms Part 5's
     load-bearing-pread finding from the other direction.
  4. In the HOT NC run (Part 5: fwd 2.024s), after V60 rules out
     begin/copyback, ~1.3s/forward remains unattributable at shell
     level — it lives inside commit+wait's GPU execution window and the
     driver's per-commit path. Next tool: Metal signposts / Instruments
     GPU trace; shell instrumentation is exhausted.


Part 7 — The Q2K nibble layout (type-42): a HOT-ONLY single-stream lever
--------------------------------------------------------------------------
The CPU hot decomposition (Part 5) shows cpumm=0.366s for 10.3GB =
28 GB/s effective — the CPU path is dequant-compute-bound, and Q2_K is
48% of those bytes (5.23GB). The sanctioned nibble layout (AGENTS.md:
byte re-arrangement, values unchanged, 2.2x unpack measured) has an
end-to-end trade-off that the file sizes confirm exactly:

  block layout: orig 84B (scales16+qs64+d2+dmin2)
                nib  148B (scales16+qs128+d2+dmin2)  = 1.76x expansion
  Q2K bytes:    5.70GB -> 10.04GB
  working set:  6.28 (main non-Q2K) + 10.04 = 16.32GB predicted
                vs 16.31GB actual nib file  <- layout inference confirmed

Consequences:
  - HOT regime (everything resident): Q2K dequant ~2.2x faster ->
    projected cpumm 0.366 -> ~0.265s, fwd ~0.37s = ~1.27x single-stream.
    The extra 4.3GB of page-cache reads is free when resident.
  - STREAMING regime: 36% more bytes from SSD -> strictly worse.
    nib is a hot-only optimization; never enable it in streaming.
  - Testability: needs 16.3GB resident — more than this machine's
    avail window all session (6-16GB). The end-to-end nib A/B joins the
    NC-hot measurement as blocked-on-clean-machine; benchmarks/
    hot_ab_27b.sh now takes the nib file as an optional second argument
    and runs the fourth arm when the window opens.

Engine support already exists (STRATUM_Q2K_NIB=<path> sidecar +
embedded type-42 detection, V55/V55.2); no engine work remains — only
the measurement.
